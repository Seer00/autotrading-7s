## Task 2 — 안전장치 조립기 · 완료

### Ruling 1: `split_config.status` 는 `IDLE | ACTIVE` 두 값뿐이다

**무엇을 결정했는가.** 계획서가 `split_config.status` 에 `RUNNING`·`PAUSED` 를
쓴 것은 잘못이다. 그 컬럼의 스키마 CHECK 는 `('IDLE', 'ACTIVE')` 이고 설계서
12.1절(725행)도 `IDLE | ACTIVE` 라고 적었다. **일시정지는 `cycle.status` 에만
존재한다.** 설정 상태는 "이 설정이 사이클을 돌리고 있는가" 만 말한다.

귀결:
- `StartCycle` → 설정 `ACTIVE`
- `PauseCycle`·`ResumeCycle`·`StopCycle` → **사이클 상태만** 바꾼다 (설정은 ACTIVE)
- 사이클 종료(정상·긴급·강제) → 설정 `IDLE`
- 대사 불일치 `INTERNAL_MORE` → **사이클** `PAUSED`, 설정은 `ACTIVE` 유지

**왜.** 설계서와 스키마가 일치하고 계획서만 어긋난다. Plan 2A 에서 19개 룰링 중
15개가 이 모양이었고, 매번 설계서가 이겼다.

**틀렸을 경우 비용.** 없다 — 스키마 CHECK 가 다른 값을 애초에 거부하며, 그
거부가 이 결함을 즉시 드러냈다(Task 2 의 첫 테스트 실행에서 10건 실패).

### Ruling 2: `create_cycle` 뒤에 `cycle.start()` 를 부르지 않는다

**무엇을 결정했는가.** `SqliteRepository.create_cycle` 은 이미 `STARTING` 상태의
사이클을 삽입하고 반환한다. 계획서의 픽스처와 Task 11 `_start_cycle` 이 그 뒤에
`cycle_mod.start()` 를 부르는데, 그것은 `STARTING → STARTING` 이므로
`IllegalCycleTransition` 이다. `start()` 는 도메인 단독 경로(`IDLE → STARTING`)의
것이다.

**왜.** 리포지토리가 이미 그 전이를 수행했다. 두 번 부르는 것은 계획서가 도메인
API 와 리포지토리 API 의 경계를 잘못 읽은 것이다.

**틀렸을 경우 비용.** 없다 — 도메인 전이표가 즉시 예외를 던진다.

### Ruling 3: 픽스처를 처음부터 `tests/conftest.py` 에 둔다

계획서는 Task 2 가 `tests/engine/conftest.py` 를 만들고 Task 4 가 그것을
`tests/conftest.py` 로 올리게 했다. 이동이 처음부터 예정돼 있었으므로 바로
최종 위치에 둔다 — 이동 커밋 하나가 사라지고, 같은 시드가 두 곳에 복제될 창이
닫힌다. 틀렸을 경우 비용: 없다.

### Ruling 4: 픽스처의 매도 완료는 홉마다 저장한다

`after_sell(to_sell_pending(s))` 를 합성해 한 번만 저장하면 `save_stage` 가
`HOLDING → SOLD` 를 거부한다(없는 전이). 두 홉을 각각 저장한다 — 2A 핸드오버 9
가 예고한 그대로이며, 설계서 9절 ④의 홉별 커밋 요구와 같은 것이다.
틀렸을 경우 비용: 없다 — 가드가 즉시 드러낸다.

### Ruling 5: 손상·불일치 격리는 사이클이 `RUNNING` 일 때만 `PAUSED` 로 전이한다

**무엇을 결정했는가.** `CorruptRowError`·`DomainInvariantError` 로 사이클을
격리할 때, 그리고 대사가 `INTERNAL_MORE` 를 판정할 때, 사이클이 `RUNNING` 이
아니면 상태를 바꾸지 않고 이벤트만 낸다. 이벤트의 `action_taken` 은 **실제로
한 것**을 말한다(`"PAUSED"` 또는 `None`).

**왜.** `STARTING` 은 `accepts_triggers()` 가 `False` 이므로 이미 격리돼 있고,
`LIQUIDATING` 을 `PAUSED` 로 되돌리면 진행 중인 긴급청산의 상태를 프로그램이
뒤집는 것이 된다 — 설계서 11.1절 ①이 "자동 트리거 즉시 정지" 를 위해 만든
상태를 자동 로직이 취소하는 셈이다. 도메인 전이표도 그 두 전이를 금지한다.

**틀렸을 경우 비용.** 낮다. 이벤트가 `action_taken=None` 으로 나가므로 사용자는
"문제가 있지만 프로그램이 상태를 바꾸지는 않았다" 를 보게 되고, 그 사이클은
어차피 트리거를 받지 않는 상태다.

### 계획서 수정 커밋

이 다섯 룰링을 계획서에 반영했다. 계획서는 실행의 기록이기도 하므로, 원장에만
남기고 계획서를 그대로 두면 다음 태스크의 전사가 틀린 값을 다시 들여온다.

## Task 4 — 주문 발주 파이프라인

### Ruling 6: 브로커 예외와 `CorruptRowError` 를 포트로 올린다

`engine/` 은 `adapters/` 를 import 할 수 없으므로(설계서 7.2절), 예외가 어댑터에만
있으면 엔진은 UNKNOWN 분기와 복원 실패를 타입으로 구분할 수 없고 결국 넓은
`except` 를 쓴다. `BrokerError` 를 공통 상위로 두고 세 예외를 `ports/broker.py`
로, `CorruptRowError` 를 `ports/repository.py` 로 옮겼다. 어댑터가 재수출하므로
2A 의 import 경로가 그대로 산다. 틀렸을 경우 비용: 없다 — 포트는 이미 `domain`
을 참조하므로 의존 방향이 바뀌지 않는다.

### Ruling 7 (배경 보안 리뷰의 지적을 받아들여 룰링을 뒤집음): 계좌 검증이 전송 실패보다 **먼저** 온다

**무엇을 결정했는가.** 계획서에서 나는 `_should_fail`(전송 계층)을 `_validate`
(거래소 계층)보다 먼저 두기로 룰링했다. **그것이 틀렸다.**

배경 보안 리뷰가 `validation-bypass` 로 지적했고, 논리가 내 것보다 강하다:
타임아웃은 "응답이 유실됐다" 는 뜻이고 "거래소가 받아줬다" 는 뜻이 아니다.
예수금이 부족한 주문은 거래소가 애초에 받지 않으므로, 검증을 나중에 두면
`TIMEOUT` 을 주입한 **모든** 시나리오에서 `validate_account` 가 조용히
무력화된다 — 예수금 1원으로 1,000,000원 주문이 등록되고 체결된다.

**이것이 왜 심각한가.** G2 시나리오 7(응답 타임아웃 → 조회 확인 → 중복 발주
없음)이 정확히 그 조합으로 돌 예정이었다. 즉 이 프로그램에서 가장 중요한 분기를
검증하는 게이트가, 동시에 한도와 보유를 **전혀** 검사하지 않는 상태로 돌게 된다.
Plan 2A 가 6건을 찾은 "통과하지만 아무것도 지키지 않는 테스트" 패턴이다.

내가 원래 내세운 근거(`fail_after` 의 의미 보존)는 유지된다: 검증에 걸린 주문은
전송 계층에 도달하지 못했으므로 카운터를 소모하지 않는다. 그 사실을 테스트로
고정했다.

**틀렸을 경우 비용.** "거부될 주문에 타임아웃이 겹친 경우" 를 시뮬레이션할 수
없다 — 실제로 존재하지 않는 조합이므로 비용이 없다.

### Ruling 8: 확인 조회 자체가 실패하면 되돌리지 않는다 (`UNKNOWN_UNRESOLVED`)

Ruling 7 을 조사하다 발견했다. 설계서 9절 ⑤ 는 응답 유실 시 `list_orders_today`
로 확인하라고 규정하지만, **그 조회도 실패할 수 있다**(키움 어댑터에서는 흔할
것이다). 그때 단계를 `WAITING` 으로 되돌리면 다음 틱에 재발주되고, 그것이 정확히
D12 가 막는 중복 주문이다.

결정: `order_log` 는 `UNKNOWN` 으로, 단계는 `PENDING` 으로 남긴다. 규칙 5 가
PENDING 단계를 판정에서 제외하므로 중복이 없고, 재시작 복구(10.1절 2)가 같은
조회로 정정한다. `SendOutcome.status` 에 `UNKNOWN_UNRESOLVED` 를 추가했다.

**틀렸을 경우 비용.** 그 단계가 재시작까지 묶인다 — `broker_order_id` 가 없어
미체결 감시가 건드리지 못한다. 대사와 화면이 그것을 드러내며, 중복 발주보다
훨씬 가벼운 비용이다.

### 배경 보안 리뷰의 1번 지적(`fail-open-control-gap`)에 대한 판단

`validate_account` 의 기본값이 꺼짐인 것은 의도다(Ruling: 2A 의 기존 시나리오
다수가 예수금 초과 매수를 전제하므로 켜면 이번 변화와 섞여 실패한다). 완화책은
게이트가 자기 소스에서 모든 `FakeBroker` 생성에 `validate_account=True` 가 있는지
확인하는 것이며, **그 검사를 `tests/engine/` 까지 넓힌다** — 한도와 긴급청산
가드가 실제로 돌아가는 곳이 거기다. Task 13 에서 구현한다.

## Task 6 — D20 강제 종료의 도메인과 쓰기 경로

### Ruling 9: `emergency_close_cycle` 은 긴급청산과 강제 종료를 모두 담당한다

두 경로가 같은 문제를 갖는다 — `force_sold` 로 전 단계를 일괄 갱신해야 하는데
`save_stage` 의 가드가 그것을 거부한다. `close_reason` 이 `EMERGENCY` 이거나
`FORCED` 인 사이클만 받고, `NORMAL` 은 거부한다. 정상 경로는 `close()` 의 보유 0
검사와 `save_stage` 의 가드를 통과해야 하며, 그것이 그 두 장치가 의미를 갖는
이유다. 틀렸을 경우 비용: 포트 메서드가 하나 늘어난다(17→19, `stage_row_id`
포함).

### Ruling 10: 단계 완전성은 **사이클의 사다리**와 비교한다 (계획서 결함)

**계획서의 검사가 연속성만 확인했다.** `expected = set(range(1, len(stages) + 1))`
는 넘겨받은 목록의 길이로 기댓값을 만들므로, 7단계 사이클에 1~3 만 쓰는 것이
통과한다. 그러면 이후 `load_stages` 가 H3(완전한 집합)으로 그 사이클을 로드하지
못하고, 사용자가 손댈 수 없는 상태가 된다 — 2A 핸드오버 7 이 경고한 fail-closed
의 대가를 스스로 만드는 셈이다.

`cycle.ladder.max_stages` 와 비교하도록 고쳤다. 사다리가 없는 경우(긴급청산은
앵커 확정 전 STARTING 에서도 시작할 수 있다 — 설계서 11.1절)는 저장된 행 수를
기준으로 한다.

**이것이 Plan 2A 가 여섯 번 찾은 패턴이다** — "통과하지만 아무것도 구별하지
못하는 검사". 내 테스트가 그것을 잡은 것은 우연이 아니라, 3-of-7 이라는 구체적인
불완전 집합을 쓴 덕분이다. 틀렸을 경우 비용: 없다.

### Ruling 11: 2A 가 남긴 "부재 고정" 테스트를 지시대로 승격했다

`test_cycle_round_trip_closed_forced_restores_status_and_reason_only` 는 2A 가
D20 필드의 **부재**를 고정하고 "Plan 2B 가 필드를 얹으면 이 assert 가 실패로
알려준다(왕복을 검증하는 테스트로 승격해야 한다는 신호다)" 라고 적어둔 것이다.
그 신호가 정확히 울렸고, 지시대로 왕복 검증으로 승격했으며 반대 방향
(`cycle_to_row` 가 두 컬럼을 내보내는지)도 함께 확인한다. 복원이 FORCED 인데
증언이 없는 행을 거부하는 테스트도 추가했다 — 스키마 CHECK 가 없던 시절의 행이나
다른 경로로 들어온 행이 조용히 통과하지 않도록.

### Ruling 12: `save_cycle` 로도 FORCED 를 쓸 수 있게 됐다 (그래도 쓰지 않는다)

`Cycle` 에 필드가 생겼으므로 `save_cycle(force_closed)` 는 더 이상
`IntegrityError` 가 아니다. **단계 쓰기는 여전히 막혀 있으므로** 그 경로만 쓰면
절반만 강제 종료된 상태를 만들 수 있다 — 2A 핸드오버 1 이 경고한 바로 그
상태다. 엔진은 언제나 `emergency_close_cycle` 을 쓴다. 그 비대칭을 테스트로
고정했다.

## Task 9 — 잔고 대사

### Ruling 13: 기준선 초기화를 `reconcile_log` 로 표현한다

설계서 11.4절은 `forced_close_qty` 를 종목별로 누적해 대사 기준선으로 삼고
사용자가 초기화할 수단을 두라고 요구한다. 초기화 시점을 담을 컬럼이 없고
스키마는 버전 1을 넘는 마이그레이션 경로가 없으므로(2A 핸드오버 5), 초기화를
`action_taken='BASELINE_RESET'` 행으로 표현하고 기준선을 "마지막 초기화 이후에
강제 종료된 수량의 합" 으로 계산한다. ISO-8601 이 사전순 = 시간순이므로 SQL 의
문자열 비교로 성립한다. 틀렸을 경우 비용: 기준선 계산이 두 테이블을 보게 되어
조금 복잡하다 — `ALTER TABLE` 단계를 새로 만드는 것보다 싸다.

### Ruling 14 (계획서에 없던 결함): 이미 `PAUSED` 인 사이클을 다시 전이하지 않는다

계획서의 대사 코드는 `if cyc.status is CycleStatus.RUNNING` 안에서만 `pause()`
를 부르되 `set_config_status` 는 조건 밖에서 불렀다. Ruling 1 로 후자를 없애면서
남은 코드가 조건을 그대로 가지고 있었지만, **그 조건이 없으면 두 번째 대사에서
`IllegalCycleTransition` 이 나고 대사 태스크가 죽는다** — 그러면 다른 종목의
불일치도 함께 놓친다. 그 회귀를 막는 테스트를 추가했다
(`test_a_paused_cycle_is_not_transitioned_again`). 5분 주기로 도는 코드에서
"두 번째 호출" 은 예외가 아니라 기본 경로다.

### 반복된 자기 실수: 문자열 검색으로 코드 성질을 단정하려 했다

"이 모듈이 `save_stage` 를 부르지 않는다" 를 `inspect.getsource` 의 문자열
검색으로 확인하려 했는데, **모듈 독스트링이 그 이름을 언급하는 것만으로
위반으로 오판했다.** 같은 실수를 `force_close` 의 `is_cycle_complete` 검사에서도
했다. 둘 다 `ast` 로 호출 그래프를 보도록 고쳤다.

교훈: "코드가 X 를 하지 않는다" 는 단정은 **AST 로** 해야 한다. 문자열 검색은
설명과 실행을 구별하지 못하며, 좋은 코드는 자기가 하지 않는 것을 문서에 적는다 —
즉 문서화가 잘 될수록 그 검사가 더 자주 틀린다.

## Task 11 — 오케스트레이터

### 계획서 결함 두 건 (테스트가 즉시 드러냄)

**`accepts_triggers` 는 프로퍼티인데 계획서가 메서드로 호출했다.**
`cyc.accepts_triggers()` 는 `bool` 을 호출하려 해서 `TypeError` 가 난다.
파이썬에서 프로퍼티를 메서드로 부르는 실수는 조용히 지나갈 수도 있었는데
(`if not <bound method>` 는 항상 False), 다행히 `bool` 은 호출 불가라서 즉시
터졌다.

### Ruling 15: 사이클 전이 명령은 멱등해야 한다

**계획서의 `_transition` 은 상태를 확인하지 않고 전이 함수를 불렀다.** 사용자가
[정지]를 두 번 누르면 두 번째 명령이 `PAUSED → PAUSED` 를 시도하고 도메인
전이표가 `IllegalCycleTransition` 을 던진다. 그 예외가 명령 소비 태스크를 죽이면
**뒤에 쌓인 명령이 전부 사라지고, 그중에 긴급청산이 있을 수 있다** — 설계서
7.1절이 `priority_q` 로 보장하려 한 즉시성이 정확히 그 지점에서 무너진다.

`allowed_from` 을 명시해 이미 목표 상태인 사이클을 조용히 건너뛴다. Task 9 의
Ruling 14(대사의 반복 pause)와 같은 결함이 다른 곳에 또 있었던 것이며, **반복
호출을 예외로 취급하는 것이 이 코드베이스에서 반복되는 내 실수**다. 주기적으로
돌거나 사용자가 버튼을 누르는 경로에서 "두 번째 호출" 은 기본 경로다.

**틀렸을 경우 비용.** `STARTING` 사이클에 [정지]를 누르면 조용히 아무 일도
일어나지 않는다 — 도메인 전이표가 그 전이를 애초에 갖고 있지 않으므로 도메인의
결정을 따른 것이고, `STARTING` 은 트리거를 받지 않으므로 실질적 차이가 없다.

### 계획서의 폴백 시나리오가 아무것도 증명하지 못했다

계획서의 WS 끊김 테스트는 스크립트 `[10_000, 9_500, 9_400]` 에 `fail_after=1` 을
써서, 첫 틱(10,000)이 1단계를 사고 끊긴 뒤 폴백이 같은 10,000 을 폴링하게 했다.
그 가격에는 발동가에 걸린 대기 단계가 없으므로 **REST 경로로 주문이 나갈 수가
없다** — "판정이 계속된다" 를 검증하려던 테스트가 그것을 검증할 수 없는 구성이
었다.

스크립트를 `[9_500, 9_400]` 으로 바꿨다: 첫 WS 틱 9,500 이 1단계를 사고(규칙 2 —
한 틱에 한 단계), 폴백이 같은 9,500 을 폴링하면 **2단계**가 발동가에 걸려 있으므로
REST 경로로 주문이 나간다. 이제 `["WS", "REST_POLL"]` 과 보유 `[1, 2]` 를 단정한다.

## Task 13 — G2 게이트

### Ruling 16 (계획서의 중대한 누락): 앵커 확정이 단계 행을 만들어야 한다

**계획서 어디에도 `stage_state` 행을 만드는 코드가 없었다.** `confirm_anchor` 는
사다리를 계산해 `cycle.ladder_json` 에 넣지만 단계 행 7개는 아무도 쓰지 않는다.
그 결과 RUNNING 사이클의 `load_stages` 가 H3(완전한 집합)으로 즉시 거부하고,
엔진은 **첫 틱부터 모든 사이클을 격리한다** — 트리거가 단 한 번도 발동하지
않는 프로그램이 된다. 게이트의 12개 시나리오가 한꺼번에 이 하나의 원인으로
실패했다.

계획서 자기검토(3회)와 12개 태스크의 단위 테스트가 이것을 놓친 이유: 모든 단위
테스트가 픽스처로 단계 행을 미리 심었다. **`StartCycle` 부터 시작하는 경로를
처음 밟은 것이 G2 게이트였다.** 이것이 게이트가 단위 테스트로 대체될 수 없는
이유의 구체적인 사례다.

`_confirm_anchor` 를 추가하고 **단계를 먼저, 사이클을 나중에** 쓴다. 그 사이에
죽었을 때 남는 상태가 다르다: 단계 먼저면 STARTING + 단계 행 → 다음 틱이 다시
확정하며 자기 치유하고, 사이클 먼저면 RUNNING + 단계 없음 → 어느 경로로도 고칠
수 없다. 설계서 9절의 "잘못 기록된 쪽이 잘못 잊힌 쪽보다 항상 낫다" 와 같은
논리다.

### Ruling 17: `allow_rebuy=True` 여도 보유 0 이면 사이클이 종료된다

게이트의 쿨다운 시나리오가 실패해서 조사했더니, 1단계를 사고 팔면 보유가 0 이
되어 `_close_if_complete` 가 사이클을 닫았다. **엔진이 맞고 내 시나리오가
틀렸다** — 설계서 4.2절(239행)이 "보유수량 0 도달 → `CLOSED(NORMAL)`, 실현손익
집계, `split_config.status = IDLE`, 다음 사이클은 사용자가 [시작]을 누를 때
현재가를 새 앵커로 시작" 이라고 규정한다.

`allow_rebuy` 는 **사이클 안에서** 같은 단계를 다시 사는 옵션이고, 사이클을
무한히 유지하는 옵션이 아니다. 플랫이 되면 앵커가 더 이상 아무것도 가리키지
않으므로 새 앵커로 다시 시작하는 것이 일관된다.

시나리오를 고쳤다: 1·2단계를 사고 **2단계만** 팔아 1단계가 보유를 유지한 채로
2단계의 재매수 쿨다운을 관측한다. 이제 사이클이 열린 상태를 단정한다.

### 게이트의 자기 단정이 구조적으로 1 만큼 어긋나 있었다

`FakeBroker(` 와 `validate_account=True` 의 등장 횟수를 비교하는 검사가, 그
테스트 함수 자신의 리터럴 때문에 항상 1 만큼 어긋났다(함수 본문에 앞의 이름은
두 번, 뒤의 이름은 한 번 나온다). **통과시키려고 상수를 더하는 순간 그 검사는
아무것도 지키지 않게 된다** — 자기 본문 앞까지만 세도록 고쳤다.

### 배경 보안 리뷰 1번(`fail-open-control-gap`)의 최종 처리

`validate_account` 의 기본값을 켜지 않았다. 대신 게이트가 자기 소스의 모든
생성에 플래그가 있는지 확인한다. **`tests/engine/` 까지 넓히지 않은 이유**:
주문을 내지 않는 대사·복구 테스트가 걸린다. 검증의 의미가 없는 곳에 플래그를
강요하면 그 플래그가 형식이 되고, 형식이 된 검사는 사람들이 이유를 모른 채
붙인다. 대신 **한도(시나리오 13)와 긴급청산(시나리오 12)을 검증하는 테스트를
게이트 안에 두었다** — 그 플래그가 실제로 무언가를 지키는 곳이 거기다.
