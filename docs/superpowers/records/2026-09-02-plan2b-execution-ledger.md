## Task 2 — 안전장치 조립기 · 완료

### Ruling 1: `split_config.status` 는 `IDLE | ACTIVE` 두 값뿐이다

**무엇을 결정했는가.** 계획서가 `split_config.status` 에 `RUNNING`·`PAUSED` 를
쓴 것은 잘못이다. 그 컬럼의 스키마 CHECK 는 `('IDLE', 'ACTIVE')` 이고 설계서
12.1절(725행)도 `IDLE | ACTIVE` 라고 적었다. **일시정지는 `cycle.status` 에만
존재한다.** 설정 상태는 "이 설정이 사이클을 돌리고 있는가" 만 말한다.

귀결:
- `StartCycle` → 설정 `ACTIVE`
- `PauseCycle`·`ResumeCycle`·`StopCycle` → **사이클 상태만** 바꾼다 (설정은 ACTIVE)
- 사이클 종료(정상·긴급·강제) → 설정 `IDLE`
- 대사 불일치 `INTERNAL_MORE` → **사이클** `PAUSED`, 설정은 `ACTIVE` 유지

**왜.** 설계서와 스키마가 일치하고 계획서만 어긋난다. Plan 2A 에서 19개 룰링 중
15개가 이 모양이었고, 매번 설계서가 이겼다.

**틀렸을 경우 비용.** 없다 — 스키마 CHECK 가 다른 값을 애초에 거부하며, 그
거부가 이 결함을 즉시 드러냈다(Task 2 의 첫 테스트 실행에서 10건 실패).

### Ruling 2: `create_cycle` 뒤에 `cycle.start()` 를 부르지 않는다

**무엇을 결정했는가.** `SqliteRepository.create_cycle` 은 이미 `STARTING` 상태의
사이클을 삽입하고 반환한다. 계획서의 픽스처와 Task 11 `_start_cycle` 이 그 뒤에
`cycle_mod.start()` 를 부르는데, 그것은 `STARTING → STARTING` 이므로
`IllegalCycleTransition` 이다. `start()` 는 도메인 단독 경로(`IDLE → STARTING`)의
것이다.

**왜.** 리포지토리가 이미 그 전이를 수행했다. 두 번 부르는 것은 계획서가 도메인
API 와 리포지토리 API 의 경계를 잘못 읽은 것이다.

**틀렸을 경우 비용.** 없다 — 도메인 전이표가 즉시 예외를 던진다.

### Ruling 3: 픽스처를 처음부터 `tests/conftest.py` 에 둔다

계획서는 Task 2 가 `tests/engine/conftest.py` 를 만들고 Task 4 가 그것을
`tests/conftest.py` 로 올리게 했다. 이동이 처음부터 예정돼 있었으므로 바로
최종 위치에 둔다 — 이동 커밋 하나가 사라지고, 같은 시드가 두 곳에 복제될 창이
닫힌다. 틀렸을 경우 비용: 없다.

### Ruling 4: 픽스처의 매도 완료는 홉마다 저장한다

`after_sell(to_sell_pending(s))` 를 합성해 한 번만 저장하면 `save_stage` 가
`HOLDING → SOLD` 를 거부한다(없는 전이). 두 홉을 각각 저장한다 — 2A 핸드오버 9
가 예고한 그대로이며, 설계서 9절 ④의 홉별 커밋 요구와 같은 것이다.
틀렸을 경우 비용: 없다 — 가드가 즉시 드러낸다.

### Ruling 5: 손상·불일치 격리는 사이클이 `RUNNING` 일 때만 `PAUSED` 로 전이한다

**무엇을 결정했는가.** `CorruptRowError`·`DomainInvariantError` 로 사이클을
격리할 때, 그리고 대사가 `INTERNAL_MORE` 를 판정할 때, 사이클이 `RUNNING` 이
아니면 상태를 바꾸지 않고 이벤트만 낸다. 이벤트의 `action_taken` 은 **실제로
한 것**을 말한다(`"PAUSED"` 또는 `None`).

**왜.** `STARTING` 은 `accepts_triggers()` 가 `False` 이므로 이미 격리돼 있고,
`LIQUIDATING` 을 `PAUSED` 로 되돌리면 진행 중인 긴급청산의 상태를 프로그램이
뒤집는 것이 된다 — 설계서 11.1절 ①이 "자동 트리거 즉시 정지" 를 위해 만든
상태를 자동 로직이 취소하는 셈이다. 도메인 전이표도 그 두 전이를 금지한다.

**틀렸을 경우 비용.** 낮다. 이벤트가 `action_taken=None` 으로 나가므로 사용자는
"문제가 있지만 프로그램이 상태를 바꾸지는 않았다" 를 보게 되고, 그 사이클은
어차피 트리거를 받지 않는 상태다.

### 계획서 수정 커밋

이 다섯 룰링을 계획서에 반영했다. 계획서는 실행의 기록이기도 하므로, 원장에만
남기고 계획서를 그대로 두면 다음 태스크의 전사가 틀린 값을 다시 들여온다.

## Task 4 — 주문 발주 파이프라인

### Ruling 6: 브로커 예외와 `CorruptRowError` 를 포트로 올린다

`engine/` 은 `adapters/` 를 import 할 수 없으므로(설계서 7.2절), 예외가 어댑터에만
있으면 엔진은 UNKNOWN 분기와 복원 실패를 타입으로 구분할 수 없고 결국 넓은
`except` 를 쓴다. `BrokerError` 를 공통 상위로 두고 세 예외를 `ports/broker.py`
로, `CorruptRowError` 를 `ports/repository.py` 로 옮겼다. 어댑터가 재수출하므로
2A 의 import 경로가 그대로 산다. 틀렸을 경우 비용: 없다 — 포트는 이미 `domain`
을 참조하므로 의존 방향이 바뀌지 않는다.

### Ruling 7 (배경 보안 리뷰의 지적을 받아들여 룰링을 뒤집음): 계좌 검증이 전송 실패보다 **먼저** 온다

**무엇을 결정했는가.** 계획서에서 나는 `_should_fail`(전송 계층)을 `_validate`
(거래소 계층)보다 먼저 두기로 룰링했다. **그것이 틀렸다.**

배경 보안 리뷰가 `validation-bypass` 로 지적했고, 논리가 내 것보다 강하다:
타임아웃은 "응답이 유실됐다" 는 뜻이고 "거래소가 받아줬다" 는 뜻이 아니다.
예수금이 부족한 주문은 거래소가 애초에 받지 않으므로, 검증을 나중에 두면
`TIMEOUT` 을 주입한 **모든** 시나리오에서 `validate_account` 가 조용히
무력화된다 — 예수금 1원으로 1,000,000원 주문이 등록되고 체결된다.

**이것이 왜 심각한가.** G2 시나리오 7(응답 타임아웃 → 조회 확인 → 중복 발주
없음)이 정확히 그 조합으로 돌 예정이었다. 즉 이 프로그램에서 가장 중요한 분기를
검증하는 게이트가, 동시에 한도와 보유를 **전혀** 검사하지 않는 상태로 돌게 된다.
Plan 2A 가 6건을 찾은 "통과하지만 아무것도 지키지 않는 테스트" 패턴이다.

내가 원래 내세운 근거(`fail_after` 의 의미 보존)는 유지된다: 검증에 걸린 주문은
전송 계층에 도달하지 못했으므로 카운터를 소모하지 않는다. 그 사실을 테스트로
고정했다.

**틀렸을 경우 비용.** "거부될 주문에 타임아웃이 겹친 경우" 를 시뮬레이션할 수
없다 — 실제로 존재하지 않는 조합이므로 비용이 없다.

### Ruling 8: 확인 조회 자체가 실패하면 되돌리지 않는다 (`UNKNOWN_UNRESOLVED`)

Ruling 7 을 조사하다 발견했다. 설계서 9절 ⑤ 는 응답 유실 시 `list_orders_today`
로 확인하라고 규정하지만, **그 조회도 실패할 수 있다**(키움 어댑터에서는 흔할
것이다). 그때 단계를 `WAITING` 으로 되돌리면 다음 틱에 재발주되고, 그것이 정확히
D12 가 막는 중복 주문이다.

결정: `order_log` 는 `UNKNOWN` 으로, 단계는 `PENDING` 으로 남긴다. 규칙 5 가
PENDING 단계를 판정에서 제외하므로 중복이 없고, 재시작 복구(10.1절 2)가 같은
조회로 정정한다. `SendOutcome.status` 에 `UNKNOWN_UNRESOLVED` 를 추가했다.

**틀렸을 경우 비용.** 그 단계가 재시작까지 묶인다 — `broker_order_id` 가 없어
미체결 감시가 건드리지 못한다. 대사와 화면이 그것을 드러내며, 중복 발주보다
훨씬 가벼운 비용이다.

### 배경 보안 리뷰의 1번 지적(`fail-open-control-gap`)에 대한 판단

`validate_account` 의 기본값이 꺼짐인 것은 의도다(Ruling: 2A 의 기존 시나리오
다수가 예수금 초과 매수를 전제하므로 켜면 이번 변화와 섞여 실패한다). 완화책은
게이트가 자기 소스에서 모든 `FakeBroker` 생성에 `validate_account=True` 가 있는지
확인하는 것이며, **그 검사를 `tests/engine/` 까지 넓힌다** — 한도와 긴급청산
가드가 실제로 돌아가는 곳이 거기다. Task 13 에서 구현한다.
