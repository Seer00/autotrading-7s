# Plan 4 — Windows 수동 검증 체크리스트

EC2 에서 검증할 수 있는 것은 전부 검증됐다. **검증되지 않은 것은 "화면이 실제로
어떻게 보이는가" 하나다** — Tkinter 위젯이 하는 일은 EC2 의 테스트에서 스텁이
삼킨다. 이 문서가 그 나머지 절반이며, G3(모의투자 검증)의 선행 절차다.

## 이미 검증된 것 (EC2, 1,029 테스트)

- 표의 모든 숫자: 보유수량·평균단가·평가손익·단계 진행·상태 표기·합계
- "목표까지 / 매수까지" 열의 방향 기호와 백분율 (설계서 목업의 일곱 줄과 일치)
- 사다리 미리보기의 모든 숫자 (설계서 14.2절 목업과 일치)
- 긴급청산·강제 종료 다이얼로그의 모든 숫자와 확인 문자열
- 프레젠터의 이벤트 소비: 불일치 유지·해소, 로그 종류 구분, 시도 이력 누적
- ASCII 렌더러: 모든 행이 같은 표시 폭(한글 포함)
- **위젯의 배선**: 모든 위젯 모듈이 import 되고 `render()` 가 뷰의 필드 이름을
  정확히 읽는다 (`tests/ui/test_widget_wiring.py`, `tkinter` 스텁)

## 검증되지 않은 것

Tk 가 실제로 그리는 것 전부 — 열 폭, 색, 폰트, 창 크기, 선택 동작, 다이얼로그의
모달 처리, 스크롤. 그리고 `mainloop()` 안에서만 드러나는 타이밍 문제.

**계획서는 위젯 층 전체를 "검증 불가" 로 두었다.** `tkinter` 스텁으로 그 범위를
"실제 Tk 동작" 으로 좁혔다 — 그래도 남은 것이 이 목록이며, 그것이 아래 항목들을
사람이 확인해야 하는 이유다.

## 기동

```
> python -m venv .venv
> .venv\Scripts\activate
> pip install -e ".[dev]"
> python -m autotrading7s --env mock --settings settings.toml ^
      --simulate 10000,10000,9500,9000,8500,9450,9980,10500
```

`settings.toml` 은 최소한 다음을 담아야 한다.

```toml
[engine]
total_limit = 21000000
```

**설정이 하나도 없으면 표가 비어 있다** — [설정관리]로 먼저 하나 등록한다.

> ⚠ **이 기동 경로의 시계는 흐르지 않는다.** `__main__.py` 가 `FakeClock` 을
> 쓰므로 재매수 쿨다운(설계서 5절 규칙 3), 미체결 3초 타임아웃(9절 ⑥),
> **그리고 5분 주기 정기 대사(10.2절)** 가 실제로 동작하지 않는다. 화면
> 확인용이며, `KiwoomClock`(설계서 18.2절, 구현 2단계)이 그것을 대체한다. 이
> 제약을 알고 확인해야 4·5번 항목을 오판하지 않는다.
>
> 정기 대사가 멈춘다는 것이 셋 중 가장 무겁다. 기동 시 복구 대사(10.1절 3)는
> **경고만 하고 정지하지 않으며**(재시작 직후의 불일치는 아직 정정되지 않은
> 주문 때문일 수 있으므로), 정지는 첫 정기 대사에 맡겨져 있다. 시계가 멈추면
> 그 인계가 일어나지 않아 `INTERNAL_MORE` 상태로 계속 돌고 매도가 반복
> 거부된다 — EC2 에서 재현했다(같은 매도가 3회 거부, `reconcile_log` 의
> `action_taken` 은 `NULL`). **D13 의 자동 정지를 이 기동 경로에서 확인할 수
> 없다**는 뜻이며, 19번 항목은 기준선 초기화만 확인하는 것으로 읽어야 한다.
> `_due_for_reconcile` 은 첫 틱을 기준선으로 삼고 `False` 를 반환하므로,
> 실전에서도 첫 정기 대사는 기동 후 첫 틱으로부터 300초 뒤다.

## 확인 항목

각 항목에 "무엇을 보아야 하는가" 와 "틀렸다면 어디를 의심하는가" 를 짝지었다.
뷰모델은 이미 테스트됐으므로 **대부분의 원인은 배선이나 Tk 설정이다.**

| 3 | 값을 입력하는 **동안** 사다리 미리보기가 갱신된다 | `StringVar.trace_add` 배선 |

| 5 | 단계 수를 `9` 로 하면 `⚠ max_stages …` 가 보인다 | 같은 분기 (`Ladder` 가 던진다) |

### 21. 가장 강한 항목 — 두 렌더러의 대조

```
> python -m autotrading7s.cli --env mock --settings settings.toml ^
      --simulate 10000,10000,9500,9000,8500,9450,9980,10500 --status
```

같은 스크립트·같은 DB 로 headless 를 돌려 나오는 ASCII 표의 숫자와 GUI 화면의
숫자가 **일치해야 한다.** 두 경로가 같은 뷰모델을 쓰므로 숫자가 다르면 **위젯의
열 매핑이 틀린 것**이다 — 사람의 눈이 아니라 두 렌더러의 대조가 판정한다.

`--db` 로 같은 파일을 가리켜 비교하면 더 정확하다.

### 22. 조용히 죽은 엔진

작업 관리자에서 프로세스를 죽이지 말고, 대신 `settings.toml` 의
`total_limit` 을 `0` 으로 두고 기동해 보라 — `load_settings` 가 거부하므로
기동 자체가 실패하고 그 메시지가 보여야 한다. 엔진 스레드가 실행 중에 죽는
경우는 배너에 붉은 `⚠ 엔진 정지: …` 가 뜨는 것으로 확인한다(그 경로는 EC2 에서
테스트됨).

**이것을 확인해야 하는 이유**: 조용히 죽은 엔진은 "프로그램이 켜져 있는데
트리거를 놓치는" 최악의 상태다(설계서 18.1 리스크 6). 사용자는 화면이 멈춘 것을
알아차리기까지 그 사실을 모른다.

## 확인 후

문제를 찾았으면 **뷰모델 쪽인지 위젯 쪽인지 먼저 가른다.** `cli --status` 의
숫자가 맞으면 뷰모델은 옳고 위젯의 배선·Tk 설정 문제다 — 그 수정은 EC2 에서
검증되지 않으므로 다시 이 체크리스트를 돌려야 한다. `cli --status` 의 숫자가
틀리면 뷰모델의 결함이고, 그것은 EC2 에서 테스트로 재현·수정할 수 있다.

**그 갈림이 이 계획의 구조가 주는 이득이다.**
