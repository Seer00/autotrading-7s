# AutoTrading 7s — 설계서

**버전** v1.0 (확정 설계)
**작성일** 2026-09-01
**기반 문서** SW 개발계획서 — 세븐스플릿(7-Split) 자동투자 프로그램 v0.1 (초안)

---

## 1. 목적과 범위

### 1.1 목적

세븐스플릿 전략 — 하나의 종목을 최대 7개 분할 단위로 나누어 하락 시 분할매수하고, 각 단위가 독립적으로 목표수익률에 도달하면 분할매도하여 평균단가를 관리하는 전략 — 을 키움증권 REST API로 자동화한다.

시판 프로그램 대비 부가기능을 배제하고 분할매수·분할매도 핵심 로직에만 집중한다.

### 1.2 범위 안

1. 사용자가 수작업으로 선정한 종목에 대해 N단계(2~7) 분할매수 자동 실행
2. 분할 단위(단계 1~N)별 독립적인 체결단가·수량·상태 관리
3. 단계별 목표수익률 도달 시 자동 분할매도
4. 실시간 시세 기반 트리거 감시 및 주문 실행
5. 매매 이력 로깅 및 상태 조회
6. 보유 중인 전 종목 상태를 한 화면에 보여주는 보유현황 표
7. 사용자가 수동으로 실행하는 긴급 청산(전량 시장가 매도)
8. 모의투자 계좌를 통한 사전 검증

### 1.3 범위 밖 (명시적 배제)

- 다종목 포트폴리오 **자동** 배분·리밸런싱 (사용자가 등록한 복수 설정의 **병렬 실행**은 범위 안)
- 자동 종목 발굴·추천·스크리닝 — 종목 선정은 전적으로 사용자의 수작업 입력
- **자동·알고리즘 기반 손절매 판단** — 전략 원칙상 배제. 사용자가 수동 호출하는 긴급청산은 별개(11절)
- 레버리지, 신용·미수 거래
- 세금 계산 자동화
- 모바일 앱, 화려한 시각화
- 단일 exe 패키징(PyInstaller)
- 백테스트 엔진

| D6 | **주문 방식: 실시간 감시 + 지정가 즉시 발주** | 모든 트리거 판단이 프로그램 안에 있어 감사 추적성 최대. 설계서 로드맵과 1:1 대응 |
| D7 | **프로세스 구조: 단일 프로세스, GUI 메인스레드 + 엔진 asyncio 워커스레드** | GUI가 멈춰도 엔진(시세 수신·주문)은 영향받지 않음. 엔진을 headless로 단독 실행 가능. 향후 프로세스 분리로 이전 시 큐를 소켓으로 교체하는 작업으로 축소 |
| D8 | **한 틱에 매수 1단계씩 순차 집행** | 갭하락으로 여러 발동가를 동시 통과할 때 한 틱에 수백만원이 나가는 것을 방지. 틱 간격이 통상 1초 미만이라 실질 지연은 무시 가능 |
| D9 | **한 틱에서 매도를 매수보다 먼저 평가** | 예수금 확보 후 매수. 목표 달성 실현이 우선 |
| D10 | **재매수 쿨다운 60초 (기본값)** | 없으면 같은 단계가 수수료를 태우며 분당 수십 번 회전 가능 |
| D11 | **`PAUSED` 상태 추가** | 설계서에 없으나 실운용 필수. "더 사지 말고 보유만 유지" 상황에서 유일한 대안이 긴급청산뿐이면 사용자는 팔지 않아도 될 때 팔게 됨 |
| D12 | **주문 응답 타임아웃 시 재발주 금지, 조회로 사실 확인** | 재발주하면 같은 단계를 두 번 매수. 실제 매매 시스템의 가장 비싼 버그 유형 |
| D13 | **대사 불일치 시 자동 보정 없이 정지** | 자동 보정은 단계별 체결가를 조용히 조작하여 이후 모든 목표가 계산의 근거를 파괴. 불일치는 사람이 확인해야 하는 사건 |
| D14 | **`cycle` 테이블 신설** | 설계서의 `split_config` → `split_state` 직결 구조는 재시작 시 이전 사이클 기록을 덮어써야 함. 사이클을 명시적 엔티티로 두어 누적 성과 이력 보존 |
| D15 | **모의/실전 DB 파일 분리** | 모의에서 검증하던 대금액 설정이 실전 전환 순간 그대로 실행되는 사고를 구조적으로 차단 |
| D16 | **장외 시간 긴급청산 요청: 거부 + 즉시 `PAUSED` 전환** | 예약 청산은 시스템이 타이밍을 정하는 쪽. 잊힌 예약이 아침에 체결되는 사고 방지 |
| D17 | **호가 단위 정규화를 domain에 포함** | 설계서에 없으나 없으면 주문이 거부됨. 목표 매도가는 올림하여 목표수익률 보장 |
| D18 | **Fake 브로커를 1급 구성요소로** | API 키 없이 개발 시작 가능. 더 중요하게는, 모의투자로 재현 불가능한 실패 경로(갭하락, 응답 타임아웃, WS 끊김)를 검증하는 유일한 수단 |
| D19 | **구현 0단계(domain + FakeBroker)를 로드맵 맨 앞에** | API 사용승인 대기 시간에 핵심 로직 전체를 검증 완료 |

## 3. 도메인 모델

### 3.1 사다리 (Ladder)

사이클 시작 시 1회 계산되어 사이클 종료까지 불변.

```python
@dataclass(frozen=True)
class Ladder:
    anchor_price: int          # 1단계 체결가. 확정 후 불변
    drop_pct: Decimal          # 단계별 하락률 (전 단계 동일)
    target_pct: Decimal        # 단계별 목표수익률 (전 단계 동일)
    max_stages: int            # 2~7
    amount_per_stage: int      # 단계당 투입금액 (원)

    def trigger_price(self, stage: int) -> int:
        """D3: 1단계 체결가 대비 누적 (등차 사다리). 호가 단위로 내림."""
        raw = self.anchor_price * (1 - self.drop_pct * (stage - 1))
        return normalize_tick(raw, Side.BUY)

    def planned_qty(self, stage: int) -> int:
        return self.amount_per_stage // self.trigger_price(stage)
```

목표 매도가는 발동가가 아니라 **실제 체결가**를 기준으로 계산되므로 `Ladder`가 아닌 별도 순수 함수로 둔다.

```python
def target_price(fill_price: int, target_pct: Decimal) -> int:
    """호가 단위로 올림 — 목표수익률 미달을 방지 (3.2절)"""
    return normalize_tick(fill_price * (1 + target_pct), Side.SELL)
```

**금액 표현 규칙**: 가격·금액은 원 단위 `int`, 비율만 `Decimal`. `float`을 섞으면 재현 불가능한 1원 오차가 발생하고 그 오차가 주문 수량을 바꿀 수 있다.

**설정 등록 시 검증**: `planned_qty(stage) == 0` 인 단계가 존재하면(발동가 > 단계금액) 설정을 거부한다. 런타임에 터지게 두지 않는다.

예시 — 앵커 9,340원, 하락 5%, 목표 5%, 7단계, 단계당 100만원:

| 단계 | 발동가 | 수량 | 투입금액 | 목표가(발동가 기준 가정) | 누적투입 |
|---:|---:|---:|---:|---:|---:|
| 1 | 9,340 | 107 | 999,380 | 9,810 | 999,380 |
| 2 | 8,870 | 112 | 993,440 | 9,320 | 1,992,820 |
| 3 | 8,400 | 119 | 999,600 | 8,820 | 2,992,420 |
| 4 | 7,930 | 126 | 999,180 | 8,330 | 3,991,600 |
| 5 | 7,470 | 133 | 993,510 | 7,850 | 4,985,110 |
| 6 | 7,000 | 142 | 994,000 | 7,350 | 5,979,110 |
| 7 | 6,530 | 153 | 999,090 | 6,860 | 6,978,200 |

총수량 892주, 총투입 6,978,200원, 전단계 보유 시 평단 7,823원(앵커 대비 -16.2%), 7단계 발동가는 앵커 대비 -30.1%.

발동가가 8,873이 아니라 8,870인 것은 호가 단위 내림(3.2절)을 적용한 결과다. 이 때문에 7단계 발동가가 정확히 -30.0%가 아니라 -30.1%가 된다.

`floor(금액/가격)` 때문에 단계별 실토입이 993,440~999,600원으로 흔들린다. **총한도 검사는 계획금액이 아니라 실체결금액 누적으로 한다**(6절).

### 3.2 호가 단위 정규화 (D17)

`domain/tick_size.py` — 순수 함수. 구간표를 단위테스트로 고정한다.

| 가격 구간 | 호가 단위 |
|---|---|
| 2,000원 미만 | 1원 |
| 2,000 이상 5,000 미만 | 5원 |
| 5,000 이상 20,000 미만 | 10원 |
| 20,000 이상 50,000 미만 | 50원 |
| 50,000 이상 200,000 미만 | 100원 |
| 200,000 이상 500,000 미만 | 500원 |
| 500,000원 이상 | 1,000원 |

> **구현 시 확인 필요**: 위 표는 2023년 KRX 호가단위 개편 기준으로 작성했다. 구현 0단계에서 KRX 규정 및 키움 API 문서로 현행 값을 확정하고, 코스피·코스닥 차이 여부를 확인한 뒤 이 절과 테스트를 갱신한다. ETF/ETN 등 종목 유형별 예외도 함께 확인한다.

**정규화 방향**

- **목표 매도가는 올림** — 9,807 → 9,810. 내림하면 설정한 목표수익률에 미달한 채로 팔린다.
- **매수 발동가는 내림** — 발동가는 판정 기준선이므로 유효 호가로만 표현한다.
- **실제 매수 지정가는 현재가**로 발주하며 현재가는 이미 유효 호가이므로 정규화가 불필요하다.

## 4. 상태기계

### 4.1 단계 (Stage)

```
                  발동가 이하 도달
        ┌────────────────────────────────┐
        │                                ▼
   ┌─────────┐   주문전송    ┌─────────────┐   체결    ┌─────────┐
   │  대기   │──────────────▶│  매수대기   │─────────▶│  보유   │
   │ WAITING │               │ BUY_PENDING │           │ HOLDING │
   └─────────┘◀──────────────└─────────────┘           └────┬────┘
        ▲       3초 미체결→취소                              │
        │       발주 거부→복구                               │ 목표가 도달
        │                                                    ▼
        │  allow_rebuy=True                        ┌──────────────┐
        │  + 쿨다운 경과                           │  매도대기    │
        │                          ┌───────────────│ SELL_PENDING │
        │                          │  전량체결     └──────────────┘
        └──────────────────────────┤                     │ 부분체결
                                   │                     └─▶ 잔량 재발주
                          ┌────────▼────────┐
                          │   매도완료      │  allow_rebuy=False
                          │      SOLD       │  → 최종 상태
                          └─────────────────┘
```

**`BUY_PENDING` / `SELL_PENDING` 의 역할**: 중복 주문을 막는 유일한 방어선.

WebSocket 시세는 초당 수십 틱이 온다. 9,480원 틱에 2단계 매수를 발주하고 응답을 기다리는 동안 9,479원, 9,478원 틱이 계속 들어온다. 상태가 `WAITING`으로 남아 있으면 그 틱마다 새 주문이 나가 몇 초 만에 수십 건이 중복 발주된다. PENDING 상태는 "이미 나갔다"는 사실을 상태로 못박아 트리거 판정 대상에서 제외시킨다.

이 때문에 **상태 전이는 주문을 보내기 직전에 먼저 기록하고 커밋한다**(9절). 순서를 뒤집으면 발주와 기록 사이의 틈에서 중복이 발생한다.

**부분체결 처리 — 매수·매도 비대칭**

| | 처리 | 근거 |
|---|---|---|
| 매수 부분체결 | 체결 수량만으로 `HOLDING` 확정, 잔량 주문 취소 | 단계는 독립 단위이므로 수량이 계획보다 적어도 로직 성립. 잔량을 쫓아 추가 발주하면 그 단계의 체결단가가 여러 개로 쪼개져 목표가 계산이 흐려진다 |
| 매도 부분체결 | `SELL_PENDING` 유지, 잔량 재발주 | 매도의 목적은 단계를 비우는 것. 중간에 멈추면 어중간한 수량이 남는다 |

### 4.2 사이클 (Cycle)

```
   ┌──────┐  사용자[시작]    ┌──────────┐  1단계 체결   ┌─────────┐
   │ IDLE │─────────────────▶│ STARTING │─────────────▶│ RUNNING │
   └──────┘                  │ 앵커미정 │  앵커 확정    │사다리고정│
      ▲                      └──────────┘               └────┬────┘
      │                            │ 1단계 미체결/취소       │
      │◀───────────────────────────┘                         │
      │                                        사용자[일시정지]│
      │  보유수량 0 도달                                 ┌────▼────┐
      │  (사이클 CLOSED, 실현손익 집계, 사용자 알림)     │ PAUSED  │
      ├──────────────────────────────────────────────────│트리거정지│
      │                                                  │보유는유지│
      │                        ┌──────────────┐          └────┬────┘
      │   전량 매도 완료       │ LIQUIDATING  │◀──────────────┘
      └────────────────────────│ 긴급청산진행 │  사용자[긴급청산]
                               │ 자동트리거OFF│  (어느 상태에서든)
                               └──────────────┘
```

**`STARTING`**: 앵커가 아직 없는 구간. 사다리를 계산할 수 없으므로 트리거 판정을 전혀 하지 않는다. 1단계가 체결되어 앵커가 확정되는 순간 `RUNNING`으로 전이하고, 그때 사다리 전체를 계산해 `cycle.ladder_json`과 `stage_state.trigger_price`에 기록한다.

**`PAUSED` (D11)**: 자동 트리거는 정지하되 보유는 유지. 대사 불일치 시 자동 진입, 사용자가 확인 후 재개.

**사이클 종료 (D4)**: 보유수량 0 도달 → `CLOSED(close_reason=NORMAL)`, 실현손익 집계, `split_config.status = IDLE`, 사용자에게 알림. 다음 사이클은 사용자가 [시작]을 누를 때 현재가를 새 앵커로 시작한다.

## 5. 트리거 판정 규칙

```python
def decide(tick: Tick, cycle: Cycle, states: list[StageState],
           ladder: Ladder, cfg: SplitConfig,
           now: datetime, market_open: bool) -> list[Decision]:
    """부작용 없음. 같은 입력 → 항상 같은 출력."""
```

순수 함수로 유지하는 이유: 네트워크·DB·시계 없이 "이 틱이 왔을 때 무슨 일이 벌어져야 하나"를 밀리초 단위로 수천 케이스 검증할 수 있다.

### 규칙 1 — 매도를 매수보다 먼저 평가 (D9)

한 틱에서 매도·매수 조건이 동시에 충족될 수 있다. 목표수익률과 하락트리거가 같은 값이면 흔히 발생한다.

```
2단계: 매도완료 → 대기 (발동가 9,500)
3단계: 보유, 체결가 9,000, 목표가 9,450

현재가 9,500 도달
  → 3단계 매도조건 충족 (9,500 ≥ 9,450)
  → 2단계 매수조건 충족 (9,500 ≤ 9,500)
  → 매도 먼저 집행
```

**하위 단계가 먼저 매도되는 것은 의도된 동작이다.** 3단계(9,000 매수 → 목표 9,450)가 1단계(10,000 매수 → 목표 10,500)보다 낮은 가격에서 목표에 닿는다. 반등 구간에서 아래쪽 단계가 차례로 정리되며 현금이 회수되는 흐름이다.

### 규칙 2 — 한 틱에 매수 1단계씩 순차 집행 (D8)

```
전일 종가 9,600 → 시가 8,400 갭하락
사다리: 9,500 / 9,000 / 8,500 / 8,000 / …
통과한 대기 단계: 2, 3, 4

틱 #1 → 2단계 매수 (체결가 8,400)
틱 #2 → 3단계 매수 (체결가 8,400)
틱 #3 → 4단계 매수 (체결가 8,400)
```

번호가 낮은 단계부터 순차로 채운다. 체결가는 발동가가 아니라 **실제 체결가**로 기록되므로 세 단계 모두 8,400원에 채워지고 각자의 목표가는 8,820원이 된다. 평단이 계획보다 낮아지는 유리한 결과이며, 사다리의 발동가는 "중복 매수 방지 기준선"으로 남는다.

### 규칙 3 — 재매수 쿨다운 (D10)

`allow_rebuy=True` 인 단계가 `SOLD` → `WAITING` 으로 복귀한 뒤, `last_sold_at` 으로부터 `rebuy_cooldown_sec`(기본 60초)이 경과해야 재매수 대상이 된다.

근거: 규칙 2의 갭하락 예시에서 8,400원에 머무는 동안, 2단계가 8,820원에 팔린 뒤 8,400원으로 돌아오면 발동가 9,500 조건을 즉시 다시 만족한다. 쿨다운이 없으면 같은 단계가 수수료를 태우며 분당 수십 번 회전한다.

### 규칙 4 — 장 운영시간 밖에서는 어떤 결정도 내리지 않음

`ClockPort`가 장중 여부를 판단하고 `decide()`는 그 결과(`market_open`)를 입력으로 받는다. 시계를 주입 가능하게 만드는 이유는 "15:29에 갭하락이 오면?" 같은 시나리오를 테스트에서 재현하기 위해서다.

> **구현 시 확인 필요**: 정규장 시간(09:00~15:30)과 휴장일 판단 방법. 휴장일 캘린더를 하드코딩할지, 키움 API 조회로 판단할지는 구현 2단계에서 API 문서 확인 후 확정한다. 잠정안: 주말·공휴일 목록을 설정 파일로 두고, 시세가 일정 시간 이상 갱신되지 않으면 휴장으로 간주.

### 규칙 5 — PENDING 상태 단계는 판정 대상에서 제외

## 6. 안전장치 (guards)

설계서 7절 2항 "무한 물타기 리스크"에 대한 코드 레벨 대응.

| 안전장치 | 규칙 | 근거 |
|---|---|---|
| 종목별 총한도 | 누적 **실체결금액**이 `split_config.total_limit` 초과 시 매수 거부 | `floor` 때문에 계획금액과 실제가 다름(3.1절) |
| 전체 총한도 | 전 종목 누적 실체결금액 상한 | 설계서 7절 2항 |
| 신용·미수 차단 | 주문 DTO에 신용 관련 필드를 **아예 정의하지 않음** | 설계서 2.2절 "코드 레벨 제약" |
| 자동 손절 차단 | `decide()`에 하락 조건 매도 분기가 **존재하지 않음** | 자동 손절매 배제 원칙 |
| 시장가 차단 | 자동 트리거 경로는 `LimitOrderRequest`만 생성 가능하며 이 타입에는 시장가 표현 방법이 없음 | 설계서 "긴급청산만 시장가" |
| 주문 빈도 제한 | 분당 최대 주문 수 상한 | 폭주 사고 차단, TR limit 대응 |
| 중복 주문 차단 | PENDING 상태 단계 제외 | 4.1절 |
| 1주 미달 차단 | 설정 등록 시 `planned_qty == 0` 단계가 있으면 거부 | 3.1절 |

**원칙을 문서가 아니라 타입으로 표현한다.** 신용 주문 필드가 DTO에 없으면 실수로 켜는 것이 불가능하다. `decide()` 안에 하락 조건 매도 분기가 없으면, 누군가 "손절 기능을 넣어달라"고 할 때 그것이 명확한 설계 변경으로 드러난다. 주석은 지워지지만 없는 필드는 실수로 쓰이지 않는다.

## 8. 브로커 포트와 어댑터

### 8.1 BrokerPort

```python
class BrokerPort(Protocol):
    async def subscribe_quotes(self, codes: list[str]) -> AsyncIterator[Tick]
    async def place_limit_order(self, req: LimitOrderRequest) -> OrderAck
    async def place_market_sell(self, req: MarketSellRequest) -> OrderAck
    async def cancel_order(self, broker_order_id: str) -> CancelAck
    async def get_order(self, broker_order_id: str) -> OrderStatus
    async def list_orders_today(self, code: str | None) -> list[OrderStatus]
    async def get_balance(self) -> Balance          # 예수금 + 보유종목
    async def get_price(self, code: str) -> int     # WS 끊김 시 폴백
```

### 8.2 주문 요청 타입 — 경로별 분리

```python
@dataclass(frozen=True)
class LimitOrderRequest:          # 자동 트리거 경로 전용
    code: str
    side: Side
    qty: int
    price: int                    # 지정가 필수. None 불가
    client_ref: UUID
    # 신용·미수 관련 필드는 존재하지 않음

@dataclass(frozen=True)
class MarketSellRequest:          # 긴급청산 경로 전용
    code: str
    qty: int
    client_ref: UUID
    reason: str                   # 사용자 입력 사유 (감사 추적)
```

자동 트리거 경로는 `LimitOrderRequest`만 만들 수 있고 이 타입에는 시장가를 표현할 방법이 없다. 설계서의 "긴급청산만 시장가" 제약이 문서상의 약속이 아니라 타입 시스템이 거부하는 사실이 된다.

`reason`이 `MarketSellRequest`에만 있고 필수인 것도 같은 발상이다. 타입이 강제하면 사유 로깅을 빼먹을 수 없다.

### 8.3 키움 어댑터 내부

```
adapters/kiwoom/
├── endpoints.toml   도메인·경로·TR(api-id) 코드
├── auth.py          TokenManager
├── rest.py          RestClient (재시도·레이트리밋·연속조회)
├── ws.py            QuoteStream (재연결·구독복원·폴백신호)
├── mapping.py       키움 필드명 ↔ 도메인 DTO
└── broker.py        KiwoomBroker(BrokerPort)
```

**`endpoints.toml`을 코드에서 분리하는 이유**는 설계서 7절 1항이다. 사양 변경이 "코드 수정 + 재테스트"가 아니라 "설정값 교체"로 끝나야 한다.

```toml
[env.mock]

ws_base   = "<공식 문서로 확정>"

[env.real]
rest_base = "<공식 문서로 확정>"
ws_base   = "<공식 문서로 확정>"

[tr]
token_issue   = "<공식 문서로 확정>"
price_current = "<공식 문서로 확정>"
order_buy     = "<공식 문서로 확정>"
order_sell    = "<공식 문서로 확정>"
order_cancel  = "<공식 문서로 확정>"
order_list    = "<공식 문서로 확정>"
balance       = "<공식 문서로 확정>"
```

> **구현 시 확인 필요**: 도메인, 엔드포인트 경로, TR(api-id) 코드, 토큰 만료 시간, TR별 호출 제한 수치, 연속조회 헤더(`cont-yn`/`next-key`) 규격, WebSocket 구독 프로토콜과 체결통보 형식. 모두 구현 1~2단계에서 [openapi.kiwoom.com](https://openapi.kiwoom.com/) 문서로 확정하고 이 파일과 본 설계서에 확정 결과를 기록한다.

**TokenManager**: 만료 60초 전 선제 갱신, 동시 갱신을 `asyncio.Lock`으로 1회로 수렴, 갱신 실패 시 지수 백오프 재시도 후 엔진에 `AuthFailed` 이벤트 발행(자동매매 정지).

**RestClient**: 재시도는 `429`·`5xx`·네트워크 오류에만 적용하고 `4xx`는 즉시 실패시킨다. 잘못된 주문을 재시도하는 것은 사고를 반복하는 것이다. TR별 토큰버킷 레이트리미터로 설계서 4.3절의 호출 제한에 대응한다.

**QuoteStream**: 지수 백오프 + 지터로 재연결하고, 재연결 성공 시 **구독 목록을 복원한다.** 이걸 빠뜨리면 연결은 살아났는데 시세가 오지 않는 조용한 실패가 된다.

### 8.4 WebSocket 끊김 → REST 폴백

```
WebSocket 정상    ─────▶  틱(source=WS), 초당 수십 건
      │ 끊김 감지 (하트비트 타임아웃)
      ▼
REST 폴링 모드    ─────▶  틱(source=REST_POLL), 3초 주기
      │  · 트리거 판정은 계속 수행
      │  · 모든 틱에 source 기록
      │  · GUI에 "시세 폴백 중" 경고 표시
      │  · 폴백 시작·종료 시각을 로그에 남김
      │ 재연결 + 구독 복원 성공

```

폴백 중에 지나간 저점은 복구할 방법이 없다(설계서 7절 3항). 이 한계를 숨기지 않고 폴백 구간을 로그에 남겨, "이 구간에는 놓친 트리거가 있을 수 있다"를 사후에 확인할 수 있게 한다.

### 8.5 Fake 브로커 (D18)

```python
class FakeBroker(BrokerPort):
    """가격 시나리오를 주입하면 그대로 재생하는 결정론적 시뮬레이터."""
    def __init__(self, script: list[int],
                 fill_mode: FillMode = FillMode.INSTANT,
                 #          INSTANT | DELAYED | PARTIAL | NEVER
                 fail_mode: FailMode = FailMode.NONE):
                 #          NONE | TIMEOUT | REJECT | DISCONNECT
```

Fake 브로커의 진짜 가치는 API 키 부재라는 임시 사정이 아니다. **모의투자 계좌로는 실패 경로를 재현할 수 없다.** 갭하락을 주문해서 만들 수 없고, 응답 타임아웃을 유발할 수 없고, WebSocket을 끊었다 붙일 수도 없다.

검증은 두 층으로 나뉜다: **로직 정확성은 Fake로, 사양 적합성은 모의투자로.**

## 9. 주문 실행 정합성

```
① decide() → BuyStage(3)
② guards 검사 (총한도·빈도·장중)   실패 시 로그만 남기고 종료
③ order_log INSERT  status=SENDING, client_ref=uuid, trigger_reason 기록
④ stage_state UPDATE  WAITING → BUY_PENDING          ← 여기서 커밋
⑤ broker.place_limit_order()
    ├─ 성공        → order_log: ACCEPTED, broker_order_id 저장
    ├─ 명시적 거부 → order_log: REJECTED, stage → WAITING 복구
    └─ 타임아웃 / 네트워크 오류
          → order_log: UNKNOWN
          → 재발주 금지 (D12)
          → list_orders_today(code)로 client_ref 대조하여 접수 여부 확인
              ├─ 접수됨 → ACCEPTED로 정정, 체결 대기 계속
              └─ 미접수 → stage → WAITING 복구
⑥ 체결 대기 (체결통보 수신 또는 get_order 폴링)
    ├─ 전량체결        → stage → HOLDING (fill_price, fill_qty)
    ├─ 3초 후 부분체결 → 잔량 취소, 체결분으로 HOLDING 확정
    └─ 3초 후 미체결   → 취소 → WAITING (다음 틱에 재시도)
```

**⑤의 UNKNOWN 분기가 이 시스템에서 가장 중요한 부분이다.** 주문을 보냈는데 응답이 오지 않았다면 두 가지 가능성이 있다 — 서버에 도달하지 못했거나, 도달했지만 응답만 유실됐거나. 여기서 "실패했나 보다" 하고 재발주하면 같은 단계를 두 번 사게 된다. 유일하게 안전한 행동은 재시도가 아니라 **조회로 사실을 확인하는 것**이다.

**③④의 순서도 같은 논리다.** 발주보다 먼저 기록하고 커밋한다. 발주 후에 기록하면 그 사이에 프로세스가 죽었을 때 "브로커에는 주문이 있는데 우리는 모르는" 고아 주문이 생기고 다음 실행에서 중복 발주로 이어진다. 반대 순서라면 최악의 경우 "우리는 보냈다고 기록했는데 실제로는 없는" 상태가 되는데, 이건 조회로 안전하게 정정할 수 있다. **잘못 기록된 쪽이 잘못 잊힌 쪽보다 항상 낫다.**

미체결 타임아웃 기본값 3초는 `settings.toml`로 조정 가능하게 둔다. 유동성이 낮은 종목에서는 더 길어야 할 수 있다.

## 10. 재시작 복구와 잔고 대사

### 10.1 시작 시 복구

강제종료·정전·블루스크린 대비로 필수.

```
1. DB에서 PENDING(BUY_PENDING / SELL_PENDING) 상태 단계 조회
2. list_orders_today()로 각 client_ref의 결말 확인
     체결됨    → HOLDING / WAITING 으로 정정
     취소·거부 → 원래 상태 복구
     기록 없음 → 원래 상태 복구 (전일 미체결은 장 마감에 자동 소멸)
3. get_balance()로 초기 동기화 대사 (불일치 시 경고, 정지하지는 않음)
4. RUNNING 사이클의 구독 복원 → 감시 재개
```

### 10.2 주기적 대사

장중 5분 간격(설계서 4.3절의 저빈도 REST 폴링).

| 상황 | 처리 |
|---|---|
| 일치 | 로그 없음 |
| 내부 < 실계좌 (외부에서 수동 매수한 듯) | 경고 로그 + GUI 배너, 자동매매 계속 |
| 내부 > 실계좌 (외부에서 수동 매도한 듯) | **해당 종목 즉시 `PAUSED` 전환** + 경고 |

**자동 보정은 하지 않는다 (D13).** 내부 기록이 실계좌보다 많으면 매도 주문이 계속 거부되어 `SELL_PENDING`에서 무한 재시도에 빠진다. 그래서 멈추는 것이 안전하다. 반대로 프로그램이 내부 상태를 실계좌에 맞춰 고치면, 단계별 체결가 정보가 조용히 조작되어 이후 모든 목표가 계산이 근거를 잃는다. 불일치는 사람이 확인해야 하는 사건으로 취급한다.

## 11. 긴급청산

### 11.1 실행 순서

설계서 3.3절의 흐름에 ②③을 추가했다.

```
사용자 → GUI [긴급청산] → 재확인 다이얼로그 → priority_q
                                                   │
   ┌───────────────────────────────────────────────▼─────────────┐
   │ 엔진: priority_q를 command_q보다 먼저 소비 (7.1절)          │
   ├─────────────────────────────────────────────────────────────┤
   │ ① 대상 사이클 → LIQUIDATING  (자동 트리거 즉시 정지)        │
   │ ② 해당 종목 미체결 주문 전량 취소             ← 추가        │
   │ ③ get_balance()로 실계좌 실제 보유수량 확인   ← 추가        │
   │ ④ MarketSellRequest(qty=실계좌수량, reason) 발주            │
   │ ⑤ 체결 확인 → 전 단계 SOLD(EMERGENCY) 일괄 갱신             │
   │ ⑥ emergency_liquidation_log 기록                            │
   │ ⑦ 사이클 CLOSED(close_reason=EMERGENCY) → 설정 IDLE         │
   └─────────────────────────────────────────────────────────────┘
```

**②를 빠뜨리면 긴급청산이 무력화된다.** 청산 시점에 하위 단계 매수 지정가 주문이 미체결로 살아 있을 수 있다. 전량 매도가 체결된 직후 그 매수 주문이 체결되면 방금 다 팔았는데 다시 보유가 생긴다. 급락 중이라면 매수 주문이 체결될 확률은 오히려 높다. "판다"는 명령은 "더 이상 사지 않는다"를 포함해야 한다.

**③에서 내부 기록이 아니라 실계좌를 신뢰한다.** 긴급청산이 호출되는 상황은 바로 "시스템 오작동이 의심되는" 상황(설계서 1.1절 7항)이다. 그 순간에 오작동했을지도 모르는 내부 기록을 근거로 수량을 정하는 것은 자기모순이다. 실계좌 수량으로 팔면 대사 불일치 상태에서도 확실히 비워진다.

**전체 종목 청산은 종목별 순차 처리.** 병렬로 발주하면 TR 호출 제한에 걸려 일부가 조용히 실패할 수 있다. 순차 처리하면 각 종목의 결과가 개별 로그로 남고 중간에 실패해도 어디까지 됐는지 명확하다.

### 11.2 재확인 절차 (설계서 7절 5항)

| 범위 | 재확인 방식 |
|---|---|
| 단일 종목 | 종목명·보유수량·현재가·예상금액·평균단가·예상손익 표시 + 취소될 미체결 건수 안내 + 사유 입력(선택) + [실행] |
| 전체 종목 | 위 정보를 종목별로 나열 + **`전체청산` 텍스트 직접 입력** 시 버튼 활성화 |

### 11.3 장외 시간 요청 (D16)

시장가 주문은 장중에만 가능하다. 장외 요청은 **거부하고, 대신 해당 설정을 `PAUSED`로 전환하는 선택지를 제공한다.**

```
  ✕ 장 운영시간이 아니어서 시장가 매도를 실행할 수 없습니다.
    (현재 17:23, 장 운영 09:00~15:30)

    대신 이 설정을 [일시정지]로 전환하면 다음 장에서
    추가 매수가 일어나지 않습니다.

                      [ 닫기 ]   [ 일시정지로 전환 ]
```

근거: 예약 청산은 시스템이 타이밍을 정하는 쪽에 가깝고(D4와 같은 원칙), 사용자가 예약을 잊으면 의도치 않은 청산이 발생한다. 요청 자체는 `emergency_liquidation_log`에 `result=REJECTED_CLOSED_MARKET`으로 기록한다.

## 12. 영속성 스키마

### 12.1 테이블

```sql
CREATE TABLE split_config (
  id INTEGER PRIMARY KEY,
  stock_code TEXT NOT NULL,
  stock_name TEXT,
  label TEXT,                       -- 종목별 복수 설정 구분 (설계서 1.1절 1항)

  updated_at TEXT NOT NULL,

CREATE TABLE cycle (                -- D14: 설계서에 없던 테이블
  id INTEGER PRIMARY KEY,
  config_id INTEGER NOT NULL REFERENCES split_config(id),

  anchor_price INTEGER,             -- STARTING 동안 NULL

  started_at TEXT NOT NULL,
  closed_at TEXT,

);

CREATE TABLE stage_state (
  id INTEGER PRIMARY KEY,

  fill_price INTEGER,
  fill_qty INTEGER,

                                    -- |CANCELED|REJECTED|UNKNOWN
  broker_order_id TEXT,
  api_code TEXT,
  api_message TEXT,
  trigger_reason TEXT NOT NULL,     -- 설계서 6절 감사 추적성

  tick_source TEXT,                 -- WS | REST_POLL

  reason TEXT,
  qty_before INTEGER,
  qty_after INTEGER,

  detail_json TEXT,
  completed_at TEXT
);

CREATE TABLE token_session (
  id INTEGER PRIMARY KEY,
  env TEXT NOT NULL,                -- MOCK | REAL

  issued_at TEXT NOT NULL,
```

### 12.2 설계서 5절과의 차이

| 항목 | 설계서 | 본 설계 | 이유 |
|---|---|---|---|
| `cycle` 테이블 | 없음 | 신설 | 재시작 시 이전 사이클 기록을 덮어쓰지 않고 누적 성과 이력 보존 (D14) |
| `ladder_json` | 없음 | 추가 | 설정을 나중에 바꿔도 과거 사이클의 사다리를 재현 가능. 감사 추적성 |
| `order_log.path` | 없음 | 추가 | 자동/수동 경로를 데이터에 영구 구분. "이 매도는 누가 결정했나"를 한 쿼리로 답 |
| `order_log.trigger_reason` | 없음 | 추가 (NOT NULL) | 설계서 6절 감사 추적성 요구를 스키마로 강제 |
| `order_log.tick_source` | 없음 | 추가 | WS/폴백 구간 구분 |
| `token_session.token` | 암호화 저장 | **저장하지 않음** | keyring에 위임. 직접 만든 암호화가 취약점의 흔한 출처 |
| `drop_pct` 등 비율 | 미지정 | TEXT (Decimal) | float 오차가 주문 수량을 바꿀 수 있음 |

`trigger_reason` 기록 형식 예:

```
stage=3 BUY | tick=8400(WS) <= trigger=9000
  | anchor=10000 drop=5% stage_gap=2
  | rule2_sequential seq=2/3 | guard_ok limit=1200000/7000000
```

### 12.3 보유현황 뷰

설계서 5절 참고사항대로 테이블이 아니라 뷰로 구성한다.

```sql
CREATE VIEW holdings AS
SELECT cfg.stock_code,
       cfg.stock_name,
       cfg.label,
       cy.id                                               AS cycle_id,
       SUM(ss.fill_qty)                                    AS total_qty,
       SUM(ss.fill_price * ss.fill_qty) / SUM(ss.fill_qty)  AS avg_price,
       COUNT(*) FILTER (WHERE ss.status = 'HOLDING')        AS holding_stages,
       cfg.max_stages,
       cy.status                                           AS cycle_status
FROM stage_state ss
JOIN cycle cy         ON cy.id  = ss.cycle_id
JOIN split_config cfg ON cfg.id = cy.config_id
WHERE ss.status IN ('HOLDING', 'SELL_PENDING')
  AND cy.status != 'CLOSED'
GROUP BY cy.id;
```

현재가와 평가손익률은 실시간 값이므로 뷰에 담지 않는다. UI가 뷰 결과와 최신 틱을 결합해 `domain/pnl.py`의 순수 함수로 계산한다.

## 13. 보안과 환경 분리

### 13.1 자격증명

앱키·시크릿·접근토큰은 **DB에 넣지 않는다.** `keyring` 라이브러리로 Windows 자격 증명 관리자에 저장한다. 현재 사용자 계정에 묶여 다른 계정이나 다른 PC로 파일을 복사해도 복호화되지 않고, 무엇보다 **직접 암호화 코드를 작성하지 않는다.**

```
keyring:  autotrading7s:{env}:app_key
          autotrading7s:{env}:app_secret
          autotrading7s:{env}:access_token

DB token_session: env, app_key 해시, 발급시각, 만료시각만 (감사 목적)
```

로깅 필터로 토큰·시크릿 패턴을 마스킹하여, 예외 트레이스백이나 요청 덤프에 자격증명이 새지 않게 한다.

### 13.2 환경 분리 (D15)

```
data/mock/autotrading7s.db      모의투자 설정·상태·로그
data/real/autotrading7s.db      실전 설정·상태·로그
```

DB 파일까지 나누는 이유는 정리 취향이 아니다. 하나를 공유하면 모의투자에서 검증하던 "단계당 1,000만원" 설정이 실전 프로파일로 전환한 순간 그대로 실행된다. 설계서 7절 4항의 "실전 전환 초기엔 소액으로 제한"을 강제하는 가장 확실한 방법은 실전 DB에 실전용 설정만 존재하게 만드는 것이다.

GUI에도 같은 원칙을 적용한다. 실전 프로파일이면 창 제목과 상단 배너를 붉게 표시한다. 자동매매 프로그램에서 "지금 실전인가 모의인가"를 헷갈리는 것은 가장 비싼 착각이다.

### 14.4 GUI를 얇게 유지하는 규칙

```
ui/  하는 일:      표시, 사용자 입력 수집, 큐에 명령 넣기
     하지 않는 일: 계산, 주문 판단, DB 쓰기, 브로커 호출
```

평가손익률 같은 표시용 계산조차 `domain/pnl.py`의 순수 함수를 호출하고, UI 파일 안에서 직접 계산하지 않는다.

이 규칙에는 이 프로젝트만의 구체적 이유가 있다. **개발은 Linux EC2에서 하는데 GUI는 Windows에서만 실행된다.** EC2에는 디스플레이가 없어 Tkinter 화면을 자동 테스트할 방법이 없다. 즉 `ui/` 안에 들어간 로직은 자동 검증이 닿지 않는 사각지대가 된다. 판단과 계산이 `domain/`·`engine/`에 있으면 EC2에서 전부 테스트되고, Windows에서 확인할 것은 "표가 제대로 그려지는가"뿐이 된다. `cli.py`(headless 기동)를 두는 이유도 같다.

## 15. 테스트 전략과 검증 게이트

### 15.1 계층

| 계층 | 대상 | 도구 | 실행 위치 | 속도 |
|---|---|---|---|---|
| 단위 | `domain/` 순수 함수 (사다리·판정·호가단위·상태전이·손익) | pytest | EC2 | 밀리초 |
| 통합 | `engine/` + FakeBroker + SQLite | pytest-asyncio | EC2 | 초 |
| 계약 | `adapters/kiwoom/` ↔ 모의투자 실서버 | pytest (수동 트리거) | Windows | 분 |
| 수동 | GUI 표시·다이얼로그 | 체크리스트 | Windows | — |

### 15.2 검증 게이트

각 관문을 통과해야 다음으로 간다.

**G1 — domain 시나리오 전부 통과**

- 사다리 계산 (앵커·발동가·수량·누적투입)
- 호가 단위 정규화 (구간 경계값, 매수 내림·매도 올림)
- 규칙 1 (매도 우선)
- 규칙 2 (갭하락 순차 매수)
- 규칙 3 (재매수 쿨다운 경계)
- 규칙 4 (장외 무동작)
- 규칙 5 (PENDING 제외)
- 단계·사이클 상태 전이 전수
- guards 전항목 (한도 경계값, 1주 미달, 빈도 제한)
- 평가·실현손익 계산

**G2 — FakeBroker로 전 사이클 + 실패 경로 통과**

- 7단계 전 사이클 (하락 → 단계별 매수 → 반등 → 단계별 매도 → 보유 0 → IDLE)
- 갭하락 3단계 동시 통과 시 틱별 순차 매수
- 매도·매수 동시 충족 시 매도 우선
- 재매수 쿨다운 동작
- 미체결 3초 타임아웃 → 취소 → 재시도
- 부분체결 매수·매도 비대칭 처리
- **주문 응답 타임아웃 → 조회 확인 → 중복 발주 없음** (9절)
- 발주 명시적 거부 → 상태 복구
- WebSocket 끊김 → REST 폴백 → 재연결 + 구독 복원
- 대사 불일치 → 자동 `PAUSED`
- 프로세스 강제 종료 후 재시작 복구
- 긴급청산 (미체결 취소 확인, 실계좌 수량 사용 확인, 장외 거부)
- 총한도 도달 시 매수 중단

**G3 — 모의투자 계좌 검증** (설계서 4.4절 완료 기준)

- 1종목 3단계 이상 분할매수·매도 사이클 무오류 완주
- 긴급청산 시나리오 1회
- 토큰 자동 갱신 1회 이상 관측
- 대사 정상 동작 확인

**G4 — 실전 계좌 소액 운영** (설계서 8절 8단계)

- 단계 수 2~3, 단계금액 최소로 제한
- 최소 1사이클 완주 후 단계적 확대

**G2가 G3보다 넓다는 점이 중요하다.** 모의투자로는 갭하락을 만들 수 없고 응답 타임아웃을 유발할 수 없다. 실패 경로는 FakeBroker에서만 체계적으로 검증된다.

## 16. 배포와 실행

```
개발  EC2 (Amazon Linux, aarch64)  ── git ──▶  운영  Windows PC
```

- 단일 exe 패키징(PyInstaller)은 범위 밖 — 로드맵에 남김

**Windows 상시 실행**: systemd가 없으므로 콘솔 상주 또는 작업 스케줄러 등록. 프로그램이 꺼져 있으면 트리거를 놓친다는 D6의 트레이드오프를 사용자에게 명시한다.

## 17. 구현 순서

설계서 8절 로드맵에 0단계를 추가했다(D19).

| 4 | `QuoteStream` + 매수 트리거 실연결 + 폴백 | 실시세 기반 매수 |

0단계를 앞에 두는 것이 실질적으로 가장 큰 변경이다. 설계서는 인증부터 시작하는데, 지금은 API 사용승인을 기다려야 하므로 그 대기 시간에 핵심 로직 전체를 검증해둘 수 있다.
